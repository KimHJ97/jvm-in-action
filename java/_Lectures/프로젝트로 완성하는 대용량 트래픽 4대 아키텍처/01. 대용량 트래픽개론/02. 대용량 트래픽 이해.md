# 대용량 트래픽 이해

## 1. 트래픽의 정의

### 1-1. 트래픽은 무엇인가

- **시스템에서 트래픽 구성**
  - HTTP 요청
  - DB 트랜잭션
  - 외부 결제 API 호출
  - 락과 대기
- **트래픽 처리 능력 측정 지표**
  - TPS: 초당 트랜잭션 수. 주로 데이터베이스와 관련된 처리량을 나타냄
  - RPS: 초당 요청 수. 주로 웹 서버나 API 서버의 선으을 평가하는데 사용

### 1-2. 트래픽은 균등하게 오지 않는다.

- 80/20 법칙: 전체 부하의 80%가 하루 중 4.8시간에 집중
- lONG tAIL은 존재하지만 피크가 인프라 비용을 결정
- 급격한 sPIKE: 0 -> 1000 TPS 전환이 10초 이내 발생 가능

### 1-3. 트래픽을 잘못 정의했을 떄의 비극

- 평균 100 TPS면 충분 -> 피크시 500 TPS에 전체 다운
- 캐시로 해결 -> Write-Heavy 결제는 캐시 무용지물
- Scale-out하면 됨 -> DB가 병목이면 서버만 늘려도 소용없음

### 1-4. 올바른 접근

- 피크 TPS 기준 설계, 평균이 아닌 99 Percentile 목표
- 부하 테스트: 실제 배포 전 피크 시나리오 5배수 검증
- 모니터링: Request latency p50/p95/p99 실시간 추적

## 2. DAU가 늘지 않았는데 왜 서버가 터졌을까

### 1-1. 1만명 접속 = 1만 TPS라는 치명적인 착각

- **왜 이런 일이 발생하는가?**
  - 영화 시작 5분전 = 이벤트 시작 시간 = 트래픽 집중
  - MAU 10만 != 서버 10대. 피크 시간대 몰림 현상이 핵심
  - CCU(동시접속) 조차 순간 버스트를 반영하지 못함
  - 사람이 2배 늘어도 입구 혼잡도는 10배 이상 증가
- **실제 사례**
  - 이벤트 페이지 오픈: 예상 1만명 -> 실제 12만 TPS 발생
  - 서버 10대면 충분하겠지 -> 3분 만에 전체 다운
  - Connection Pool 예상 100 -> 실제 필요 1200

### 1-2. 보이지 안흔 트래픽: 클릭 없이도 요청은 날아간다.

- **숨겨진 트래픽 발생원인**
  - 자동 새로고침: 30초마다 = 분당 2회 \* 전체 사용자
  - 폴링/실시간: Websocket Heartbeat, 상태 체크, 알림 확인
  - 앱 백그라운드: 위치 동기화, 푸시 토큰 갱신, 세션 유지
  - Third-Party SDK: Analytics(3초마다), 광고(10초마다) 채팅

### 1-3. TPS만 보면 안된다: 요청의 무게가 시스템을 결정헌다.

- **요청 무게의 실체**
  - Health Check는 2ms, 결제는 3500ms, 1750배 차이
  - 결제 1건 = DB 조회 1000건에 해당하는 부하
  - JOIN 5개 + 서브쿼리 = 단순한 SELECT의 50배 CPU 사용
  - 외부 API 호출 = 블로킹 시간 동안 Connection/Thread 점유
